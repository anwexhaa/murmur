Murmur

A real-time feed and fanout service in Go. Posts land in Postgres, travel an event bus, and are pushed into per-user timelines in Redis — except for creators too large to push to, whose posts are merged in at read time. The whole project exists to produce one honest number: the follower count where pushing stops being worth it.

Section 03

The three problems worth building for

Strip these out and Murmur is a CRUD app with extra processes. They are the reason the project is worth three weeks, and they are what an interviewer will actually ask about.

1 · Fanout does not survive contact with a large creator

Push-on-write is the obvious design: when someone posts, write that post ID into every follower's timeline. It is also quadratic in the wrong place. A creator with 500,000 followers turns one publish into 500,000 Redis writes — which is fine at 3am and catastrophic when ten of them post at once. Pull-on-read is the opposite trade: publishing is free, but every timeline read has to go fetch from each large creator you follow and merge the results.

Neither is right. The answer is a threshold, and the point of the project is that you measure yours instead of copying a number from a conference talk.

2 · One viral post becomes one hot Redis key

Every timeline containing that post hydrates the same post:{id} key. Redis shards by key, so a single popular post pins one shard's CPU while the rest of the cluster idles — and a cache expiry under load produces a stampede, where a thousand concurrent misses all go to Postgres for the same row.

Two fixes, both small, both measurable: an in-process LRU in front of Redis so hot posts never leave the gateway, and singleflight so N concurrent misses for the same key collapse into one downstream fetch. The k6 scenario that proves it is the interesting artefact.

3 · GraphQL makes N+1 the default, not the exception

A 50-post timeline asking for author { handle, avatarUrl } and viewerHasLiked naively fires 101 resolver calls, each its own gRPC round trip. The fix — per-request batching via DataLoader — is well known. The valuable part is that you build the naive version first in Phase 2, record the number, then fix it in Phase 5 and record it again. A before/after is worth ten times what an "I used DataLoader" bullet is worth.

Section 04

Data model

Postgres is the only source of truth. Redis holds nothing that cannot be rebuilt from it — which is what lets you flush the entire cache during a demo and watch the system heal.

Postgres

users          id uuid pk · handle citext unique · display_name · created_at
follows        follower_id uuid · followee_id uuid · created_at
               pk (follower_id, followee_id)
               index (followee_id, follower_id)  -- "who follows X", paged
posts          id ulid pk · author_id uuid · body text · created_at · deleted_at
               index (author_id, created_at desc)
author_stats   user_id uuid pk · follower_count bigint · fanout_mode enum(push,pull)
outbox         id bigserial · aggregate_id · type · payload jsonb
               created_at · published_at null
               index (published_at) where published_at is null
refresh_tokens id uuid pk · user_id · token_hash · family_id · used_at · expires_at

Why ULIDs for post IDs. They sort lexicographically by creation time, so the Redis ZSET score falls out of the ID itself, cursor pagination needs no extra column, and a merge across sources is a plain comparison. A random UUID would force you to carry a timestamp everywhere and keep the two in sync.

Why an outbox and not a direct publish. Writing the post and publishing post.created are two systems. Do them separately and there is a window where the post exists but no timeline ever hears about it — a silent, unreproducible bug. Writing the event into the same transaction as the post, then relaying it, converts that into at-least-once delivery, which the fanout worker is built to tolerate.

Redis keyspace

tl:{user_id}            ZSET  post_id → score(ts_ms)   capped at 800 via Lua
author:{id}:recent      ZSET  post_id → score(ts_ms)   capped at 200
post:{post_id}          STRING hydrated post JSON       TTL 10m
heavy                   SET   author ids above threshold, refreshed by worker
rl:{user_id}:{bucket}   STRING token-bucket counter     Lua, Phase 7

The property that makes redelivery safe. ZADD with the same member is idempotent — re-running it changes nothing. So when JetStream redelivers post.created after a worker dies mid-fanout, the retry is harmless by construction. You do not need dedup tracking; you need to notice that you don't, and say so in the README. This is the same instinct as the idempotency keys in Settle, arrived at from the other direction.

01

The domain, over gRPC

3 days

A real social graph you can drive entirely from the command line, with no HTTP anywhere.

Build

  • api/proto/social/v1/social.proto — CreateUser, Follow, Unfollow, ListFollowers (paged), CreatePost, BatchGetPosts, BatchGetUsers.

  • Server interceptors: request ID, slog context, panic recovery, and a deadline check that refuses work with under 50ms left.
  • A seeding command: cmd/seed generates N users and a power-law follower distribution. You will need 500k-follower accounts in Phase 4, so build it properly now.
  • Integration tests with testcontainers-go against a real Postgres.

02

GraphQL gateway — deliberately naive

3 days

A working public API, built the obvious way, instrumented well enough to prove the obvious way is slow.

Build

  • gqlgen, schema-first. Types: User, Post, Timeline, PageInfo. Queries: me, user(handle), post(id), userPosts. Mutations: createPost, follow, unfollow.
  • gRPC clients held for the process lifetime, never per-request. Propagate the request deadline into every call.
  • Field resolvers written the naive way on purpose: Post.author does its own GetUser call.
  • Instrument it: a per-request counter of downstream gRPC calls, exported to Prometheus and logged at the end of each request.
  • OpenTelemetry traces spanning gateway → gRPC → Postgres, so the waterfall is visible in a screenshot.

03

Fanout on write

4 days

Posting becomes an event. Timelines are built asynchronously, and killing a worker mid-fanout loses nothing.

Build

  • Outbox table plus a relay goroutine in social-svc: claim unpublished rows with FOR UPDATE SKIP LOCKED, publish to JetStream, mark sent. Batch it.
  • JetStream stream POSTS, subject post.created, file storage, durable pull consumer with explicit ack and a max-deliver limit into a DLQ subject.
  • fanout-worker: for each event, page through ListFollowers, pipeline capped-ZADD into each tl:{follower}. One Lua script does ZADD + ZREMRANGEBYRANK atomically so the cap can never be violated by an interleaving.
  • Worker concurrency: a bounded worker pool over a channel, with errgroup and a semaphore — not an unbounded go func() per event.
  • timeline-svc: ZREVRANGE tl:{user} → BatchGetPosts → return. Gateway's timeline query now hits it.
  • Metrics: fanout_duration_seconds histogram labelled by follower-count bucket, fanout_followers_total, consumer pending depth.

Go you'll meet

goroutineschannelsworker poolssemaphoreselect + ctx.Doneredis pipelining

Done when

  • A post by a 1,000-follower account reaches every follower's timeline, verified by reading all 1,000.
  • docker kill the worker halfway through a fanout, restart it: every follower ends with exactly one copy of the post. Write this up as a test, not a manual check.
  • A poisoned event lands in the DLQ instead of blocking the consumer forever.

Capture this number

Fanout p99 per follower-count bucket (100 / 1k / 10k / 100k), and end-to-end publish-to-visible latency. Also: entries lost across ten kill-restart cycles. That should be zero, and zero is the whole point.

04

The hybrid cutover

3 days

Break the push design on purpose, then fix it with a threshold you measured rather than guessed. This is the centrepiece of the project.

Build

  • First, break it. Have the 500k-follower account post. Record how long fanout takes, how far the consumer falls behind, and what happens to read latency while it runs. Screenshot the Grafana panel. This is evidence, not a detour.
  • author_stats maintained on follow/unfollow; a fanout_mode the worker reads, cached in-process with a short TTL and refreshed from the heavy set.
  • Worker routing: below threshold → push as before. At or above → skip the fanout entirely, write only author:{id}:recent.
  • timeline-svc read path becomes a merge: fetch tl:{me}, fetch author:{a}:recent for each heavy author I follow (in parallel, via errgroup), k-way merge by score, dedupe, truncate to the page size.
  • A property test on the merge function, in the spirit of your QuickCheck work: for any set of input streams, the output is sorted descending, contains no duplicates, and is exactly the top-k of the union.
  • Then find the threshold. A Go benchmark that sweeps follower counts and measures push cost against the read-merge cost it saves. Plot it. Pick the crossover. Write down why.
  • Handle the transition: an account crossing the threshold upward needs no backfill; crossing downward does. Decide and document the policy.

Go you'll meet

go test -benchgenerics for mergecontainer/heaperrgroup fan-outproperty testing

Done when

  • The 500k-follower post is visible to every follower, and publish no longer degrades timeline reads for anyone else.
  • The merge property test passes over hundreds of generated cases.
  • docs/adr-001-fanout-threshold.md exists and cites your own benchmark, not a blog post.

Capture this number

The crossover threshold, the benchmark that produced it, and the write-amplification reduction for the largest account. Also the read-side cost you accepted in exchange — a trade you can state in both directions is the one that reads as real engineering.

05

Caching and the read path

3 days

Collect the "after" numbers. Kill the N+1, survive a viral post, and make cache invalidation correct rather than hopeful.

Build

  • DataLoader per request (dataloadgen) for users, posts and like-state. Loaders live in request context and die with it — a process-lifetime loader is a correctness bug that leaks one user's data into another's response.
  • Three-tier post hydration: in-process LRU → Redis post:{id} → BatchGetPosts over gRPC.
  • singleflight around every miss, so a thousand concurrent requests for a viral post produce one downstream fetch.
  • Invalidation: on edit or delete, remove from Redis and publish post.updated; each gateway instance drops its local LRU entry on receipt. Accept that the local tier is eventually consistent and bound the window with a short TTL.
  • Cursor pagination on the ULID, replacing any offset pagination.
  • k6 scenarios: baseline (steady mixed read/write) and viral (5k VUs converging on one post).

Go you'll meet

singleflightsync.RWMutexgenericsLRU cachespprofbenchmark profiling

Done when

  • Timeline requests issue a small constant number of downstream calls regardless of page size.
  • Under the viral scenario, downstream fetches for the hot post stay flat as virtual users climb.
  • An edited post never serves stale content beyond the documented TTL, and there is a test that proves the bound.

Capture this number

Calls per request before and after (your Phase 2 number is the "before"). Cache hit ratio by tier. Redis ops on the hot key with and without singleflight. Timeline p99 before and after. These four are the reason the project exists.

06

Real-time subscriptions

3 days

Live timeline updates that work when the publisher and the subscriber are on different pods, and that a slow client cannot stall.

Build

  • GraphQL subscription timelineUpdates over the graphql-transport-ws protocol.
  • The fanout worker publishes a light notification to timeline.{user_id}; each gateway subscribes only to the subjects for users currently connected to it. Any pod can serve any user, because NATS is the routing layer — this is the part people get wrong with an in-memory hub.
  • Per-connection hub: a bounded buffered channel, a writer goroutine, ping/pong keepalive, and a hard read deadline.
  • Backpressure policy, decided and documented: when a client's buffer fills, drop the oldest and send a gap signal telling the client to refetch. Never block the publisher on a slow reader.
  • Resume on reconnect: the client sends its last seen cursor, and the server replays from tl:{user} up to a bounded window.
  • Connection metrics: live connections, send-buffer high-water mark, dropped frames, delivery latency.

Go you'll meet

websocketsbounded channelsselect with defaultcontext cancellationgoroutine leak detection

Done when

  • Three gateway replicas: publish through replica A, receive on a client connected to replica C.
  • A client that deliberately stops reading gets disconnected or gapped, and every other client's latency is unaffected.
  • goleak confirms no goroutines survive a closed connection.

Capture this number

Concurrent connections held per pod and the memory that costs, publish-to-client delivery p99 across pods, and the effect of one deliberately slow consumer on everyone else's p99 — ideally none.

07

Auth and hardening

2 days

Make the public surface safe to point at the internet, including the attack that is specific to GraphQL.

Build

  • Argon2id password hashing with per-user salt and constant-time comparison.
  • Short-lived JWT access tokens plus refresh-token rotation: tokens stored hashed, grouped into a family, and reuse of a spent token revokes the whole family. This is the detection mechanism, not a nicety.
  • gRPC auth interceptor: the gateway signs an internal assertion carrying the caller's identity; backend services verify it and never trust a raw header.
  • Per-user token-bucket rate limiting in Redis Lua — the same technique as Orion Queue's atomic pop, applied to a different problem.
  • Query complexity and depth limits. An unbounded GraphQL API lets one request ask for followers-of-followers-of-followers and take the cluster down. Set a complexity budget, reject over it with a useful error, and write the test that fires the malicious query.
  • Input validation at the edge, persisted-query allowlist as a stretch, introspection off in production.

Go you'll meet

crypto/subtleargon2jwtgqlgen extensionsmiddleware chains

Done when

  • Replaying a used refresh token kills the session family and is covered by a test.
  • A deliberately nested query is rejected by the complexity limiter, with a test that asserts the rejection.
  • A backend service refuses a call that did not come through the gateway.
08

Deploy, observe, prove

3 days

Get it onto a cluster and turn three weeks of work into a README someone will actually read.

Build

  • Multi-stage distroless Dockerfiles; images well under 30MB.
  • Kubernetes manifests or a small Helm chart: Deployments, Services, HPA on the gateway, a separate HPA on the fanout worker keyed to JetStream consumer lag — reuse the KEDA pattern from Helios.
  • Readiness probes that actually check dependencies; liveness probes that don't.
  • PodDisruptionBudget and a graceful-shutdown window long enough to drain WebSocket connections.
  • GitHub Actions: test → build → push → deploy, with the k6 baseline run as a gate.
  • Grafana dashboard: fanout latency by bucket, timeline read p99, cache hit ratio, consumer lag, live connections. Screenshot it into docs/.
  • Chaos experiments: kill a fanout worker under load; sever Redis and confirm reads degrade to Postgres rather than erroring; partition NATS and confirm the outbox drains on recovery.
  • README with the architecture diagram, the threshold ADR, and a results table of every number you captured.

Go you'll meet

Done when

  • The full system runs on a real cluster and survives a pod kill during a load test with zero failed requests.
  • Redis going away degrades the read path instead of breaking it.
  • The README's results table is complete, with the measurement method next to each number.

If you need to ship sooner. Phases 0–5 are the resume-critical core: they contain Go, gRPC, GraphQL, NATS, the hybrid fanout, and every before/after number. That's fifteen working days. Phases 6–8 make it a system rather than a service — worth doing, but you could apply after Phase 5 with an honest "subscriptions and cluster deploy in progress" and lose very little.
